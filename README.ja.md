# flight-hotel-search

[English](README.md) · [繁體中文](README.zh-TW.md) · **日本語**

Google Flights / Google Hotels からリアルタイムの航空券価格とホテル料金を取得します。
[Claude Code](https://claude.com/claude-code) のスキルとして使えるほか、CLI スクリプト単体
でも実行できます。

**核心となる知見：** Google は検索結果の最初の画面を HTML にサーバーサイドレンダリングして
いるため、ほとんどのクエリは `curl` だけで完結します——ブラウザを起動する場合と比べて約 20 倍
高速です。ブラウザが必要なのは「その価格を実際に誰が販売しているか」という層だけで、そこ
だけが動的に読み込まれます。

**繁体字中国語・英語・日本語**の 3 つのインターフェースに対応し、通貨は独立して設定できます。

## 動作要件

`bash`、`curl`、`python3`。サードパーティ製パッケージ、API キー、ビルド手順のいずれも不要です。

開発・テスト環境は Python 3.14 / macOS です。バージョン依存の構文は使用しておらず、shell
スクリプトも GNU/BSD 固有の `date` フラグを避けているため、より古い Python 3.x や Linux でも
動作するはずですが、これらの組み合わせは未検証です。

## クイックスタート

```bash
# 往復（都市名を使うとその都市圏の全空港が対象になります）
scripts/gflight.sh 東京 台北 2026-10-01 2026-10-05

# 片道（復路の日付を省略）
scripts/gflight.sh NRT TPE 2026-11-15

# ホテル：地名 チェックイン チェックアウト 大人の人数
scripts/ghotel.sh 京都 2026-11-24 2026-11-26 2

# 期間内で最も安い日を探す
python3 scripts/gscan.py flight TYO TPE 2026-10-01 2026-10-31 --nights 4
python3 scripts/gscan.py hotel 京都 2026-11-20 2026-11-30 --nights 2

# フルサービスキャリアのみで往復を検索（専用スクリプトが必要な理由は「落とし穴」参照）
python3 scripts/gnolcc.py 東京 大阪 2026-03-15 2026-03-20
```

### 予約経路（航空会社公式サイト vs OTA）

「その運賃を誰が販売しているか」は唯一サーバーサイドレンダリング**されない**層であり、
`curl` では取得できず実際のブラウザ操作が必要です。詳細な手順は
[`references/booking-sources.md`](references/booking-sources.md) にあります（MCP 経由で
ブラウザを操作する、Claude Code スキル向けの内容です）。CLI スクリプトのみを使う場合は不要です。

## 言語と通貨

すべて環境変数で制御します。既定値は `zh-TW` / `TWD` / `tw` です。

| 変数 | 既定値 | 説明 |
|---|---|---|
| `GFH_LANG` | `zh-TW` | `zh-TW`、`en`、`ja` |
| `GFH_CURR` | 言語に追従 | 言語とは独立して設定可能 |
| `GFH_REGION` | 言語に追従 | Google の `gl` パラメータ |
| `GFH_UA` | 通常のブラウザ文字列 | 独自の識別子を使う場合に設定 |

```bash
GFH_LANG=ja scripts/ghotel.sh 金沢 2026-11-24 2026-11-26 2
GFH_LANG=ja GFH_CURR=JPY scripts/gflight.sh 東京 台北 2026-10-01 2026-10-05

# 言語と通貨は独立しています：日本語インターフェースで米ドル建て表示
GFH_LANG=ja GFH_CURR=USD scripts/ghotel.sh 京都 2026-11-24 2026-11-26 2
```

`GFH_LANG=ja` で日本のホテルを検索すると、英語インターフェースよりも地域の事業者が多く、
施設名もより正確に取得できる傾向があります。

## 仕組み

Google は結果データを `aria-label` 属性に**自然言語の文**として書き込んでおり、その語順は
言語ごとに全く異なります：

```
zh-TW  來回總價 <price> 新台幣起。 搭乘<airline>的直達航班。 … 於<airport>出發，…
en     From <price> US dollars round trip total. Nonstop flight with <airline>. Leaves <airport> …
ja     往復の合計金額 <price> 円～。 <airline> が運航する直行便。 … <airport>発、…
```

ホテルはさらに顕著で、価格と名称の前後関係が逆転します：

```
zh-TW  <hotel>，價格 $<price> 起                 <- 名称が先
en     Prices starting from $<price>, <hotel>     <- 価格が先
ja     <hotel>、NT$<price>～                       <- 名称が先
```

したがって単一の汎用的な正規表現では対応できません。`scripts/locales.py` が言語ごとに
パターン一式を保持し、名前付きグループ（`name`、`price`、`dep`、`arr` など）を使うことで、
パーサー自体は言語非依存に保たれています。

## 落とし穴

以下はいずれも**エラーを出さずに誤った数値を返す**もので、クラッシュするよりはるかに厄介
です。すべてドキュメントからの推測ではなく、実際にレスポンスを比較して発見したものです。

**Google は認識できないパラメータを黙って無視します。** 400 を返すことはなく、既定値を使って
静かに結果を計算します。したがってクエリパラメータを自分で組み立てる場合は必ず対照実験を
行ってください——「明らかに違う結果になるはず」の入力（年末年始 vs 平日）に変えてみて、
結果が変わらなければそのパラメータは効いていません。

**ホテルの日付と通貨は URL パラメータではなく `ts=` の protobuf 内にあります。**
`?checkin=2026-12-30&checkout=2027-01-03` と書いても、返ってくるのは**翌日 1 泊**の、
見た目には全く正常なページです。同様に `curr=USD` もホテルでは無視され、`ts` 内の通貨
フィールドが優先されます。実測では同一施設が、偽の日付で 1,348、実際の年末年始 4 泊で
4,207 と 3.1 倍の差が出ました。`scripts/gtsgen.py` が `ts` を正しく生成するため、スクリプト
経由であれば問題ありません。

**人数は数値ではなくフィールドの繰り返し回数で符号化されています。** 大人 1 名が
`{1:{1:3}}` 1 組、2 名ならそれを 2 回繰り返します。人数を数値フィールドに入れても黙って
無視され、常に 2 名分の料金が返ります。1 名利用の料金は通常 20〜30% 安くなります。

**「往復合計 X〜」は往路の航空会社しか示していません。** この価格は最も安い復路と組み合わせて
算出された下限値であり、その復路は多くの場合 LCC です。そのため結果一覧を航空会社で絞り込んでも、
絞られるのは往路だけです。`gnolcc.py` はこのために存在します——航空会社名をクエリ文字列に
渡すことで、Google はそのフィルタを**両方の区間**に適用します。実測（TPE-KIX）では、一覧上は
あるフルサービスキャリアが 11,711 と表示されていましたが、実際は往路のみ同社で復路は LCC
であり、両区間とも同社の真の往復運賃は 13,819 でした。

**航空会社名は現在のインターフェース言語と一致している必要があります。** `China Airlines` は
`hl=zh-TW` では 0 件、`中華航空` は `hl=en` では 0 件になります。`locales.py` が言語ごとに
適切なリストを保持しており、一度に絞り込めるのは 1 社のみです。

**ホテルの価格は 1 泊あたりであり宿泊総額ではありません。** またスキャナは最安値ではなく
**中央値**で日付を並べます——最安の物件はゲストハウスやカプセルであることが多く、安いベッドが
1 つ出ただけで、実際には相場が高い日が「お得な日」に見えてしまうためです。

**Google は市場のすべてではありません。** 掲載されるのは提携パートナーです。LCC 自社サイトの
期間限定セールや、地域の OTA の多くは表示されません。「Google 上で最安」は「市場で最安」では
ありません。

**サーバーサイドレンダリングされるのは最初の画面のみ**で、航空券は約 20〜24 件、ホテルは
18〜20 件です。相場の把握には十分ですが、網羅的な一覧ではありません。

## テスト

```bash
python3 -m unittest discover -s tests -v
```

35 件のテスト。ネットワーク接続もサードパーティ製テストランナーも不要です。すべて
`tests/fixtures.py` の**合成データ**上で動作します（`Example Air`、`範例航空` など、架空の
航空会社・ホテル・価格）。空港名のみ実在のものを使用していますが、これは対応表の検証対象
そのものであり、かつ地名は事実だからです。

理解しておくべき点が 2 つあります：

- このテストが検証するのは**自分たちの正規表現が設計通りに動くか**であって、Google の出力が
  今もそれに一致するかではありません。Google がラベルの文言を変更した場合、テストは緑のまま
  実際のクエリだけが空を返します。したがって `locales.py` のパターンを変更する際は、実際の
  ページでも検証してください。
- 取得元サイトのページ内容はリポジトリに一切保存していません。実際の HTML をそのまま
  フィクスチャとしてコミットするのが最も簡単ですが、それは他者のページをバージョン管理に
  取り込むことを意味します。

大半のケースは実際に発生したバグに対応しており、テスト名かコメントにその旨を記載しています。
このテストスイートは変異テストによって有効性を検証済みです——過去の 4 つのバグ（飲み込まれる
`DEAL` 接尾辞、小さすぎるラベル長上限、`ts` からの通貨欠落、CJK 幅計算の削除）を再導入すると、
いずれの場合もテストが失敗します。

macOS 上の Python 3.9、3.13、3.14 で検証済みです。

## 言語を追加する

1. `scripts/locales.py` の `LOCALES` にあるエントリをコピーします。
2. **実際にその言語でページを取得し**、本物の `aria-label` 文字列と自分のパターンを突き合わせ
   ます。文法からの推測で書かないでください。
3. パーサーが 1 件以上を返すことを確認します。Google は解析失敗を通知しません——返るのは空の
   リストだけで、地名の綴り間違いやレート制限と見分けがつきません。

言語追加時の注意点が 2 つあります。英語のラベルは CJK より大幅に長く（直行便での実測値：
英語 233〜277 文字に対し中国語 108〜131 文字）、抽出する文字数の上限は言語ごとに設定する必要
があります——上限が小さすぎると文末（到着時刻、所要時間）が何のエラーもなく静かに欠落します。
また英語は通貨記号ではなく名称を綴るため（`From <price> US dollars`）、`$` で照合しても 1 件も
見つかりません。

## Claude Code スキルとして使う

このリポジトリは [Claude Code](https://claude.com/claude-code) のスキルも兼ねています。
ディレクトリごと `~/.claude/skills/` に置けば CLI が読み込みます。

| ファイル | 用途 |
|---|---|
| `SKILL.md` | Claude Code が読み込むスキル定義。繁体字中国語で記述されています。 |
| `SKILL.en.md` | 英語版。**使用するには 2 つのファイル名を入れ替えてください**——Claude Code は `SKILL.md` しか読みません。 |
| `evals/evals.json` | スキルの起動条件と挙動の評価データ。Claude Code の `skill-creator` が使う形式です。単体テストではなく、CLI スクリプトの利用にも不要です。 |
| `references/local.md` | **任意、バージョン管理対象外。** このファイルを作成すると `SKILL.md` が Claude に読み込みを指示します。マシン固有の接続設定——結果を旅程ファイルに書き込むのは自分のどのスキルか、自分のファイル規約など、公開リポジトリに埋め込むべきでない内容を置く場所です。 |

スキル定義は引き継ぎ先を意図的に特定していません——「それらの文書を管理しているスキル」に
結果を渡す、という書き方をしています。具体的な設定を ignore 対象の `references/local.md` に
置くことで、公開されるスキルは可搬性を保ち、自分の環境設定は private なまま保てます。

CLI スクリプトは単体で動作し、上記のいずれも必要としません。

## サポートとメンテナンス

ベストエフォートでメンテナンスしており、サポートや応答時間の保証はありません。

このプロジェクトが何に依存しているかをご理解ください：パーサーは Google のレンダリング出力を
読み取っているため、**先方の文言やマークアップが変わると壊れ、しかもその失敗は静かです**——
クエリはエラーではなく空のリストを返します。これは「いつか」の問題であって「起きるかどうか」
の問題ではありません。結果が突然空になった場合は、レート制限と決めつける前に `locales.py` を
新しく取得したページと照合してください。

再現可能なクエリを添えたバグ報告を歓迎します。言語追加の pull request も歓迎しますが、
「言語を追加する」の手順に従ってください——特に、パターンは実際のページで検証すること、
および取得したページ内容をコミットしないことが必須です。
